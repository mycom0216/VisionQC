# VisionQC — AI 머신비전 외관 불량검사 프로그램

> 이미지를 ONNX 모델로 검사해 양품/불량을 판정하고 이력을 저장·조회하는 C# WPF 데스크톱 프로그램

| | |
|---|---|
| 기간 | 2026.11 ~ (진행 중) |
| 형태 | 개인 프로젝트 |
| 기술 | C# (.NET 10), WPF·MVVM(CommunityToolkit.Mvvm), OpenCvSharp, ONNX Runtime, SQLite, xUnit · Python(PyTorch/torchvision, onnxruntime, OpenCV) |
| 코드 | 이 저장소. 문서 `docs/`, 학습 `training/` |

## 1. 왜 이 주제인가

C#·WPF 기반 외관검사 신입 채용공고(세이지리서치 등)와 경력 공고(이노메트릭스, 옵트에이아이)를 살펴보니 공통 요구가 **C# 데스크톱(WPF) + OpenCV 영상처리 + 딥러닝 추론 + 검사 이력/현장 운영성**이었다. 이를 한 프로젝트에서 보여주도록 설계했다. (조사 범위·한계는 [분석서](01_분석서.md) §1.3)

## 2. 구조

```
이미지 소스 ─▶ [큐] ─▶ 전처리 ─▶ ONNX 추론 ─▶ 판정 ─▶ SQLite 저장 ─▶ WPF 표시
(IImageSource)        (IPreprocessor) (IInferenceEngine) (IJudge) (IResultRepository)
```

- 계층: Core(외부 의존 없음) ← Imaging / Inference / Data / App. 인터페이스로 분리해 **모델·입력 소스를 바꿔도 UI를 고치지 않는다**.
- 학습은 Python(`training/`), 앱은 C#에서 ONNX Runtime으로 추론만 한다.

## 3. 직접 설계·구현한 부분

| 주제 | 내용 |
|---|---|
| ERROR 판정 분리 | 손상 이미지·추론 실패·점수 NaN을 양품(OK)으로 흘리지 않고 `ERROR`로 기록. 검사 1장 실패가 전체를 멈추지 않음 |
| 판정과 추론 분리 | 점수를 저장해 두면 모델을 다시 돌리지 않고 임계값만 바꿔 재판정 가능. 경계값(점수=임계값)은 NG — 미검출이 오검출보다 비용이 크다는 기준 |
| 비동기 파이프라인 | `Channel` 기반 생산자-소비자, 큐 용량 제한(메모리 폭주 방지), 취소 시 처리 중인 1장은 끝까지 저장, 저장 실패는 집계하고 계속 |
| 파이썬↔C# 계약 | 클래스 순서(0=양품), 전처리(INTER_AREA·RGB·ImageNet 정규화), 출력(logits→softmax)을 문서화하고 `OnnxParityTests`로 점수 일치(오차 < 1e-4) 검증 |
| 클래스 순서 함정 | 폴더 알파벳순이면 `defect`가 0번이 되어 판정이 뒤집힘 → 코드에서 고정하고 테스트 |
| 학습 데이터 누수 방지 | 클래스 비율을 유지한 고정 분할(seed·`split.json`), 시험셋은 에폭·임계값 선택에 쓰지 않음, 임계값은 검증셋 재현율 기준으로 선택 |
| 증강 판단 | metal_nut은 "뒤집힌 너트"가 불량 종류라 뒤집기 증강이 양품을 불량처럼 만든다 → `--no-flip` |
| 추적성 | 모델 버전 = 파일 SHA-256 앞 12자리, 회차마다 모델·임계값 기록 |
| 통계 화면 | 일별 양품률·불량 유형·처리시간 분포. 양품률 = OK÷(OK+NG)(판정 불능 ERROR는 분모 제외), 일 단위는 UTC가 아니라 **로컬 달력 날짜** 기준, p95는 최근접 순위. 집계 계산을 DB·UI와 분리(`StatsCalculator`)해 단위 테스트 |
| 재판정·정정 | 정정을 `result_review`에 **행으로 추가**(원 판정 불변, 가장 나중 정정이 유효)해 감사 가능하게 설계. 임계값 슬라이더로 **저장된 점수만으로** 판정 변화(NG→OK/OK→NG)와, 정정된 건을 정답으로 본 재현율·정밀도를 즉시 미리보기 → 엔지니어가 데이터로 임계값을 조정. 점수 NaN 등 ERROR는 임계값 평가에서 제외 |
| 로그인·권한·감사 | 작업자/엔지니어/관리자 3역할. 비밀번호는 **PBKDF2-HMAC-SHA256(600,000회)+계정별 salt**, 고정 시간 비교. 틀린 비밀번호와 없는 아이디는 같은 메시지·같은 계산 시간(아이디 열거 방지), 5회 실패 10분 잠금. 권한 없는 탭은 숨기되 동작마다 서비스에서 재검사하고, 관리 작업은 세션 값이 아니라 **저장소의 현재 역할**로 확인해 이미 비활성화된 관리자의 열린 창도 막는다. 최초 관리자는 계정이 0개일 때만 원자적 SQL로 생성(동시 실행 테스트). 자기 자신·마지막 관리자는 비활성화 불가 |
| 감사 로그 | 로그인·잠금·검사 시작/종료·정정·설정 변경(전→후 값)·사용자 변경을 기록. 저장소 API는 추가·조회만. 기록 실패가 검사·정정을 막지 않게 분리하고 화면에 실패를 표시. 비밀번호는 어디에도 남기지 않는 것을 테스트로 확인 |
| 설정·ROI | 설정은 임시 파일에 쓴 뒤 교체(쓰는 도중 꺼져도 기존 파일 유지), 깨진 파일·범위 밖 값은 앱이 죽지 않고 보정/기본값으로 시작하며 사유를 화면에 표시. ROI는 **비율로 저장**해 해상도가 달라도 같은 영역, 전처리에서 잘라 리사이즈. 실행 인자 덮어쓰기가 파일에 새어 들어가지 않도록 저장값/적용값을 분리 |
| 직접 찾은 버그 | 시연 캡처에서 OK 37·총 50인데 양품률이 72%(정답 74%). 건수를 올리기 전에 양품률을 계산해 한 건씩 늦게 갱신되던 문제 → 값이 바뀔 때 알리도록 고치고 양품률 규칙을 `QualityMath`로 통일, 회귀 테스트 추가 |

## 4. 결과 (MVTec AD `metal_nut`)

데이터: 양품 242장, 불량 93장(bent·color·flip·scratch). 분할 train 235 / val 50 / test 50(불량 14).
모델: ResNet18 사전학습 미세조정, 20에폭, 224px, 뒤집기 증강 끔.

| 임계값 | 불량 검출 | 놓친 불량 | 오검출 |
|---|---|---|---|
| 0.678 (검증셋 재현율 ≥ 0.98 기준으로 선택) | 13/14 | 1 | 0 |
| 0.5 (참고) | 14/14 | 0 | 0 |

- 앱 시연(시험셋 50장, 임계값 0.678): OK 37 / NG 13 — 학습 단계 지표와 일치. 화면: [검사](screenshots/01_검사화면_metal_nut.png), [이력](screenshots/02_이력화면.png), [재판정](screenshots/04_재판정화면.png), [설정](screenshots/06_설정화면.png), [관리·감사로그](screenshots/07_관리화면_감사로그.png), [최초 관리자 생성](screenshots/05_최초관리자생성.png), [통계](screenshots/03_통계화면.png)
- 처리시간: 모델 실행만 평균 9.4ms·p95 11.2ms(ONNX Runtime CPU). 앱 통계 화면 기준(전처리+추론+판정, 같은 50장 1회 실행) 평균 23.0ms·p95 28ms·최대 60ms — 반복 측정은 하지 않았다.

## 5. 테스트

- C# 122건(재판정·정정 19건, 인증·설정·ROI 60건 포함): 판정 경계값·ERROR·재판정, 파이프라인(손상 이미지·취소·저장 실패·다중 워커), 전처리(채널 순서·한글 경로), ONNX 수학, SQLite 왕복, 종단(폴더→SQLite), 통계(양품률·로컬 날짜 경계·p95·기간 집계)
- 파이썬 19건: 분할·전처리·지표·MVTec 변환
- 파이썬↔C# 점수 일치: 실제 모델과 점수가 0.5 부근인 모델(민감도 높음) 모두 통과

## 6. 한계 (정직하게)

- 시험셋이 50장(불량 14)이라 **불량 1장이 재현율을 약 7%p 움직인다**. 일반화 근거로 쓰기엔 부족하다. 임계값 0.678도 불량 14장짜리 검증셋에서 정해 다소 높게 잡혔다.
- metal_nut **한 카테고리·한 촬영 환경**의 결과이며 실제 생산라인 성능이 아니다. MVTec AD는 원래 이상 탐지 벤치마크이고 여기서는 지도 분류로 바꿔 썼으므로 공식 수치와 비교할 수 없다. 데이터는 CC BY-NC-SA 4.0(비상업)이라 저장소에 포함하지 않았다.
- 구현 범위: 분류 모델, 폴더 입력, 로그인·권한·감사, 검사·이력·재판정·통계·설정·관리 화면. **미구현** — 불량 위치 박스 표시, 카메라 입력, 연속(폴더 감시) 검사, 노이즈 제거, 결과 이미지 저장 경로 설정. 통계의 "불량 유형" 영역은 분류 모델이 유형을 내지 않아 비어 있다 ([명세서](03_요구사항명세서.md))
- 계정 보안의 한계: **세션 만료(자동 로그아웃) 없음**, 비밀번호 자체 복구·이중 인증·계정 삭제 없음. 감사 로그는 API 수준에서만 추가 전용이라 DB 파일을 직접 고치면 막을 수 없다(변조 방지 아님). 외부 보안 점검은 받지 않았고 단일 PC 로컬 DB 기준이다.
- ROI는 슬라이더로만 지정하며(이미지 위 드래그 UI 없음), 쓰려면 **같은 영역으로 학습한 모델**이어야 한다. 현재 모델은 전체 이미지로 학습했으므로 ROI를 켠 채 검증하지 않았다.
- 성능 목표(500ms)는 모델 실행 기준으로만 측정했고, 100장 p95·메모리 누수 점검은 하지 않았다. 앱 화면은 수동 시연과 일회성 UI 자동화 스크립트로만 확인했고 저장소에 포함된 자동 UI 테스트는 없다.
- 실제 산업용 카메라·조명·PLC·장비는 다루지 않았다(카메라 추상화 인터페이스까지만 설계).

## 7. 면접 예상 질문 대비

1. **불량을 양품으로 놓치는 것과 양품을 불량으로 보는 것 중 무엇이 더 위험한가?** → 놓친 불량이 출하되므로 재현율 우선. 그래서 경계값을 NG로 두고, 임계값을 검증셋 재현율 기준으로 정했다. 대신 오검출은 재검사 비용으로 흡수한다.
2. **판정 불능은 어떻게 처리하나?** → `ERROR`를 별도 상태로 두고 사유를 기록. 양품으로 처리하지 않는다.
3. **모델을 교체하면 앱을 고쳐야 하나?** → `IInferenceEngine` 뒤에 있어 UI 수정은 없다. 단, 출력 규약(클래스 순서·logits)·전처리가 같아야 하며 이를 문서와 일치 테스트로 지킨다.
4. **시험셋 지표를 어떻게 믿나?** → 시험셋은 학습·에폭 선택·임계값 선택에 쓰지 않았다. 다만 표본이 작아 신뢰구간이 넓다는 점을 한계로 밝혔다.
5. **왜 ONNX Runtime인가?** → C#에서 딥러닝 추론의 표준 경로이고, PyTorch 없이 배포 가능. 내보낸 모델이 PyTorch와 일치하는지(최대 오차 3.8e-6)와 C# 추론이 파이썬과 일치하는지를 각각 확인했다.
6. **다음 단계는?** → 검출(YOLO) 모델로 불량 위치와 유형을 표시하고(통계의 불량 유형도 채워진다), 세션 만료와 연속 검사를 추가한 뒤 100장 p95와 메모리 점검으로 성능을 실측한다.
